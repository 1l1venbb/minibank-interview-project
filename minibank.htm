MiniBank — Coding Challenge Specification

Domain Overview

MiniBank is a simplified banking REST API. Your task is to implement it from scratch using the provided starter project.

The domain has three core concepts:

  • Accounts — each account belongs to an owner, is identified by an IBAN, holds a balance, and is denominated in a single currency. Accounts are either CHECKING or SAVINGS.
  • Transfers — a transfer moves funds from one account to another. It records the source IBAN, target IBAN, amount, and the timestamp when it was created.
  • Transactions — each transfer produces per-account ledger entries. When a transfer executes, the source account gains a debit transaction and the target account gains a credit transaction. These are the transaction history entries returned by GET /api/accounts/{accountId}/transactions.

Understanding the relationship between transfers and transactions is important: a single transfer creates two transaction records (one on each side), and the transaction type depends on whether the bank account (ID 1) is involved.

Technology Stack

This challenge uses Java 25, Spring Boot 4, Spring Data JPA, and an H2 in-memory database. The starter project is pre-configured with these dependencies.

For setup instructions and project structure details, see the starter project's README.md -- it will help you get running quickly.

System Bank Account

A bank account with ID 1 and IBAN RO49AAAA1B31007593840000 is pre-seeded at application startup. It serves as the system's funding source.

Key characteristics:

  • Unlimited funds — transfers from the bank account never fail due to insufficient balance.
  • Funding user accounts — to add money to a user account, create a transfer from the bank account (as sourceIban) to the user account (as targetIban). This is the only way to deposit funds into the system.
  • No ledger — transactions involving the bank account are NOT recorded on the bank account's side. Only the user account's transaction history is updated. Specifically, the counterpartyIban field on those transactions is null (the bank account is the counterparty, but its IBAN is not exposed in the ledger).

API Endpoints

All endpoints return errors with appropriate HTTP status codes (4xx). See Error Responses in Business Rules for the response format.

1. POST /api/accounts

Create a new bank account.

Request body:

{
  "ownerName": "Alice Popescu",
  "iban": "RO49AAAA1B31007593840000",
  "currency": "EUR",
  "accountType": "CHECKING"
}

Fields:

  • ownerName — required string
  • iban — required string; must be a valid IBAN
  • currency — one of RON, EUR, USD, GBP
  • accountType — one of CHECKING, SAVINGS

Success response:

{
  "id": 2,
  "ownerName": "Alice Popescu",
  "iban": "RO49AAAA1B31007593840000",
  "currency": "EUR",
  "accountType": "CHECKING",
  "balance": 0.00,
  "createdAt": "2026-02-26T10:00:00Z"
}
  • id is a sequential Long, auto-generated
  • balance starts at 0.00
  • createdAt is the account creation timestamp

Create a transfer between two accounts.

Request body:

Fields:

7. GET /api/accounts/{accountId}/transactions

Retrieve the per-account transaction history for a single account, in chronological order.

Query parameters:

  • page — page index, zero-based (default: 0)
  • size — number of transactions per page (default: 10)

Response: A paginated envelope (same shape as GET /api/accounts) with a content array of transaction objects.

Each transaction object has the following fields:

FieldTypeDescription
idLongUnique transaction identifier
timestampTimestampWhen the transaction was recorded
typeStringOne of DEPOSIT, WITHDRAWAL, TRANSFER_IN, TRANSFER_OUT
amountDecimalAmount in the account's currency
currencyStringAccount currency at the time of the transaction
balanceAfterDecimalAccount balance immediately after this transaction was applied
counterpartyIbanStringThe other account's IBAN; null when the counterparty is the bank account (ID 1), for both DEPOSIT and WITHDRAWAL transactions
transferIdLongReference to the transfer that created this transaction

Transaction types:

  • DEPOSIT — funds received from the pre-seeded bank account (ID 1) into this account
  • WITHDRAWAL — funds sent from this account to the pre-seeded bank account (ID 1)
  • TRANSFER_IN — funds received from another non-bank account
  • TRANSFER_OUT — funds sent to another non-bank account

Transaction Type Decision Matrix

Use the following table to determine which transaction type to record on each side of a transfer:

The counterpartyIban field is null when the counterparty is the bank account (ID 1), for both DEPOSIT and WITHDRAWAL transactions.

8. GET /api/exchange-rates

Retrieve the current exchange rates used for currency conversion.

Response: An object mapping currency codes to their RON-equivalent rates. The rates are loaded from exchange-rates.yml at application startup.

Response fields:

  • Each key is a currency code (EUR, USD, GBP, RON)
  • Each value is a decimal representing the amount of RON equivalent to 1 unit of that currency
  • RON itself has a rate of 1.00 (base currency)

The automated test suite will validate against the exact values in exchange-rates.yml. Do not modify those values.

Business Rules

IBAN Validation

Account IBANs must be valid IBANs. The IBAN must conform to the international standard for the account's country, including correct format and checksum. Accounts with invalid IBANs must not be created.

IBAN Uniqueness

Each IBAN may only be associated with one account. Attempting to create an account with an IBAN that is already in use must be rejected with HTTP status 409 Conflict.

SEPA Transfers

Only transfers between accounts whose IBANs belong to SEPA member countries are allowed. If either the source or target IBAN belongs to a non-SEPA country, the transfer must not be created. You are responsible for knowing which countries are SEPA members.

Account Types and Daily Limits

CHECKING accounts: No special restrictions beyond standard validations.

SAVINGS accounts: A daily outgoing transfer limit of 5,000 EUR equivalent applies. This limit aggregates all outgoing transfers from the account within a single calendar day.

  • For a SAVINGS account denominated in EUR, the limit is 5,000 EUR.
  • For a SAVINGS account denominated in another currency (RON, USD, GBP), the limit is calculated by converting the outgoing amount to its EUR equivalent using the current exchange rates, then summing across all outgoing transfers on that calendar day.
  • A transfer that would cause the cumulative daily outgoing total to exceed 5,000 EUR equivalent must not be created.

Example: RON-denominated SAVINGS account, daily limit 5,000 EUR equivalent

Transfer 1: Send 10,000 RON
  EUR equivalent = 10,000 / 4.97 = 2,012.07 EUR (HALF_EVEN rounding, scale 2)
  Cumulative daily total: 2,012.07 EUR -- under limit
  Result: Allowed

Transfer 2: Send 15,000 RON (same calendar day)
  EUR equivalent = 15,000 / 4.97 = 3,017.10 EUR (HALF_EVEN rounding, scale 2)
  Cumulative daily total: 2,012.07 + 3,017.10 = 5,029.17 EUR -- exceeds 5,000 EUR
  Result: Rejected

Edge cases:

  • The daily limit resets at midnight (calendar day boundary).
  • The limit applies per account, not per owner — two SAVINGS accounts owned by the same person each have independent 5,000 EUR daily limits.
  • CHECKING accounts are not subject to daily limits.

Currency and Exchange Rates

Supported currencies: RON, EUR, USD, GBP.

The base currency for all conversions is RON. When transferring between accounts with different currencies, the conversion formula is:

convertedAmount = amount * (sourceToRON / targetToRON)

Where sourceToRON is the exchange rate of the source currency (RON per 1 unit), and targetToRON is the exchange rate of the target currency.

Example: transferring 100 EUR to a GBP account:

  • sourceToRON = 4.97 (EUR rate from exchange-rates.yml)
  • targetToRON = 5.73 (GBP rate from exchange-rates.yml)
  • convertedAmount = 100 * (4.97 / 5.73) = 86.74 GBP

The pinned rates in src/main/resources/exchange-rates.yml are:

EUR: 4.97   (1 EUR = 4.97 RON)
USD: 4.56   (1 USD = 4.56 RON)
GBP: 5.73   (1 GBP = 5.73 RON)
RON: 1.00   (base currency)

Rounding: All monetary amounts must use BigDecimal with HALF_EVEN rounding (banker's rounding) at scale 2. Do not use float or double for any monetary calculation.

For cross-currency transfers:

  • currency in the transfer record reflects the source account's currency
  • exchangeRate is the effective rate used (sourceToRON / targetToRON), rounded to scale 6 with HALF_EVEN
  • convertedAmount is the amount credited to the target account, rounded to scale 2 with HALF_EVEN

Concurrency

Handle concurrent access to accounts correctly. The system must be safe when multiple transfers involving the same account are processed simultaneously — for example, two simultaneous debits must not both succeed if the combined amount exceeds the available balance.

The implementation strategy is your choice.

Idempotency

Support idempotency keys for duplicate transfer prevention. When a POST /api/transfers request includes an idempotencyKey, a subsequent request with the same key must return the original transfer response without creating a new transfer or modifying any balances.

The implementation strategy is your choice.

Insufficient Funds

An account balance must never go negative. Transfers that would bring a source account balance below zero must not be created.

Error Responses

All error responses use the following shape:

{"status": "REJECTED", "message": "descriptive text"}

Fields:

  • status — always "REJECTED" for error responses
  • message — human-readable description of the error

Use appropriate HTTP status codes following standard HTTP semantics (e.g., 400 for validation errors, 404 for not found, 409 for business rule conflicts).

Requests that fail validation or violate business rules do not create or modify any resources. Only successful operations are stored and returned.
